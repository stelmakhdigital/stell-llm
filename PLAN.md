# stell-llm — план разработки

> Собственный рантайм инференса LLM для NVIDIA Tesla V100 (SM70, SXM2, NVLink),
> объединяющий сильные стороны 1Cat-vLLM и project-maya и устраняющий их недостатки.

Версия плана: 0.2 (draft)

Подход к разработке: **полноценный продукт с первого дня**. Мы не строим урезанные
MVP-версии и не откладываем «на потом» подсистемы — вся целевая архитектура
проектируется сразу, модули разрабатываются параллельными потоками и
интегрируются по мере готовности. Релиз — только когда готов полный контур.

---

## 1. Цель и не-цели

### Цель
Один рантайм, который:
- работает с **любой** поддерживаемой моделью (dense и MoE), а не привязан к одной,
- задействует **NVLink (SXM2)** для тензорного и экспертного параллелизма,
- умеет **tiering весов**: VRAM → pinned RAM → NVMe (как в project-maya),
- даёт **скорость Volta-ядер** уровня 1Cat-vLLM,
- включает полный сервисный контур: OpenAI- и Anthropic-совместимый API,
  дашборд-монитор, калибровка, бенчмарк-харнесс, качество-гейты.

### Не-цели (сознательно)
- AMD ROCm, Windows (можно позже, как отдельные порты — не в основном контуре),
- обучение/fine-tuning — только инференс,
- поддержка GPU младше SM70 — вторично.

### Что устраняем у прототипов (недостатки → решения)

| Проблема | 1Cat-vLLM | project-maya | Решение в stell-llm |
|---|---|---|---|
| Привязка к одной модели | — (реестр vLLM, но тяжёлый стек) | + (только GLM-5.3-Flash) | декларативные определения моделей + слой tiering, независимый от архитектуры |
| Multi-GPU без NVLink/TP | + (TP/PP по NVLink) | + (только PCIe, layer-split) | NCCL TP/EP по NVLink — в ядре, а не в обвязке |
| Expert tiering VRAM/RAM/SSD | — | + (но без prefetch-предсказания) | отдельный модуль `tiers` с предиктором и io_uring |
| Динамические эксперты vs CUDA Graphs | частично (полный graph у dense) | — | фиксированные VRAM-слоты + DMA, graph по константной разметке |
| Prefill на V100 слабый | + (Flash-V100 ~70 TFLOP/s) | — (≈500 tok/s) | SM70-attention ядра как отдельная библиотека |
| Спекулятивный драфт не для V100 | + (DFlash2 на V100 доказан) | + (драфтер только RTX30/A100+) | драфтер как плагин с верификацией FP32 и автоотключением по калибровке |
| Качество при tiering-инференсе не проверяется | — | — | обязательные quality-gates на интеграционных срезах |
| Тяжёлая экосистема (форк vLLM) / непрозрачный UX | форк upstream | свой стек, но непрозрачный | собственное ядро, минимальные зависимости, открытые ADR |

## 2. Целевая архитектура (весь продукт целиком)

```
stell-llm/
├── docs/                     # ADR, дизайн-документы, бенчмарк-контракты
├── src/
│   ├── engine/               # C++20: планировщик, continuous batching, CUDA Graphs,
│   │                         #   пулы слотов, спекулятивный контур
│   ├── kernels/              # CUDA: SM70-attention (FP32 QK/PV), MoE gather/scatter,
│   │                         #   dequant NVFP4/W4A16, KV-квант E4M3, драфтер-ядра
│   ├── tiers/                # Tier Manager: VRAM-slots / pinned-RAM / NVMe (io_uring),
│   │                         #   политика LRU/LCU, router-lookahead prefetch
│   ├── models/               # декларативные описания архитектур + лоадеры
│   │   ├── registry/         #   dense llama/qwen, MoE glm/qwen-moe/deepseek-класс
│   │   └── weights/          #   safetensors, GGUF, NVFP4-W4A16, stell-tier layout
│   ├── parallel/             # NCCL TP / EP / PP, комм-паттерны по NVLink, KV-streaming
│   ├── serve/                # OpenAI-совместимый API, Anthropic-совместимый API
│   │                         #   (/v1/messages), стриминг tool-calls, SSE, CORS
│   ├── ui/                   # дашборд-монитор: VRAM-карта, tier-статистика,
│   │                         #   hit-rate prefetch, сессии, логи
│   ├── calibrate/            # авто-калибровка железа: границы tier'ов, включение
│   │                         #   драфтера/квантов KV только там, где это быстрее
│   └── bench/                # бенчмарк-харнесс + контракт измерений + quality-gates
├── python/                   # тонкий control-plane: конфиг, health, метрики (FastAPI)
└── tests/                    # юнит + golden-тесты логитов + операторные replay-тесты
```

Ключевые принципы:
1. **Ядро — C++20/23 + CUDA** (полный контроль над памятью, слотами, DMA). Python — только тонкий control-plane.
2. **Модели — декларативно**: описание архитектуры + лоадер форматов. Новая модель = файл описания (+ ядро, если новая операция).
3. **Tiering не знает про модель**: модуль `tiers` оперирует «тензорными группами» с ролями (expert/attn/kv).
4. **Калибровка — арбитр**: любое ускорение (драфтер, KV-квант, prefetch) включается только если измеримо быстрее на данном железе.
5. **Бенчмарк — контракт**: каждое изменение меряется по протоколу раздела 5.

## 3. Технологические решения (ADR-заготовки)

| # | Решение | Выбор | Альтернатива и почему нет |
|---|---|---|---|
| ADR-1 | Ядро | C++20 + CUDA 12.x (SM70) | PyTorch-стек (как vLLM): быстрее старт, но тянет ограничения и не даёт контроля пулов слотов |
| ADR-2 | Коммуникации | NCCL (TP/EP) поверх NVLink; P2P DMA для tiering | самописные копирования — не нужны |
| ADR-3 | Форматы весов | safetensors (HF) + GGUF + собственный «stell-tier» layout для NVMe | экзотические форматы — через конвертер |
| ADR-4 | KV-кеш | FP16 базово; E4M3-8бит (софтовый квант) опционально | FP8 нативно на V100 нет — только эмуляция |
| ADR-5 | Графы | CUDA Graph для decode, фиксированные пулы | torch.compile — вне ядра |
| ADR-6 | API | один процесс на порту 8080: `/v1/chat/completions` + `/v1/messages` | отдельный прокси — не нужен |
| ADR-7 | Сборка | CMake, CI GitHub Actions (CPU-пути тестируются без GPU) | — |

## 4. Спецификация продукта и потоки работ

Вместо последовательных MVP-фаз — **пять параллельных потоков**, каждый доводит
свой модуль до полного целевого вида из раздела 2. Точки синхронизации —
**интеграционные срезы** (вклейка готовых модулей в общий контур), а не урезанные
версии продукта.

### Поток A — ядро и ядра (engine + kernels)
Полный объём: планировщик continuous batching (≥8 сессий), пулы слотов, CUDA Graphs,
спекулятивный контур (draft + FP32-верификация), SM70-attention (FP32 QK/PV,
layout-реплей, цель ≥70 TFLOP/s операторно), MoE gather/scatter, dequant-ядра
NVFP4/W4A16, KV-квант E4M3, KV-streaming для длинного контекста.
**Готовность потока**: все ядра проходят операторные replay-тесты; engine гоняет
dense-модель в 1 GPU и MoE с фиксированным пулом экспертов в 1 GPU.

### Поток B — tiering (главная фишка)
Полный объём: Tier Manager (VRAM-slots / pinned RAM / NVMe io_uring), stell-tier
layout на NVMe, политика LRU/LCU со статистикой маршрутизатора, router-lookahead
prefetch, метрики hit-rate и пауз слоёв.
**Готовность потока**: MoE-модель больше VRAM (FP16-профиль) декодируется с
p95-паузой между слоями ≤ 5 мс и предиктором prefetch ≥ 60% попаданий.

### Поток C — параллелизм (parallel)
Полный объём: NCCL TP (dense), EP-шардирование экспертов по NVLink, PP для
dense > VRAM, комбинированные схемы (PP×TP / PP×EP), KV-streaming между узлами.
**Готовность потока**: TP4 dense масштабируется ≥3.2× от TP1; GLM-класс на
4–8×V100-SXM2 проходит TP/EP-контуры без PCIe-бутылочных горл.

### Поток D — модели и форматы (models + weights)
Полный объём: реестр dense (llama/qwen-класс) и MoE (glm/qwen-moe/deepseek-класс),
лоадеры safetensors + GGUF + NVFP4-W4A16, stell-tier layout, конвертеры.
**Готовность потока**: минимум 3 архитектуры (1 dense, 2 MoE) в полном контуре
с tiering; golden-тесты логитов против HF-референсов.

### Поток E — сервисный контур (serve + ui + calibrate + bench)
Полный объём: оба API с tool-calls и стримингом, CORS, health/метрики, дашборд
(VRAM-карта, tier-статистика, hit-rate, сессии), калибровщик (границы tier'ов,
драфтер, KV-квант — вкл/выкл по замеру), бенчмарк-харнесс + quality-gates
(GSM8K-32, HumanEval-32, PPL).
**Готовность потока**: полный контур агента (Claude Code-класс) работает
без ручного вмешательства; дашборд отражает состояние всех модулей.

### Интеграционные срезы (не MVP — вклейка модулей в полный контур)
- **Срез 1**: A×D — dense-модель в 1 GPU, оба API живых.
- **Срез 2**: +C — TP4 dense по NVLink.
- **Срез 3**: +B — MoE с tiering (модель > VRAM).
- **Срез 4**: +E-финал — спекуляция, калибровка, дашборд, quality-gates на всём контуре.
Каждый срез — это интеграция готовых модулей полного дизайна, а не сокращённая
версия продукта: недостающие модули просто ещё не вклеены, их контуры уже
спроектированы и разрабатываются параллельно.

### Definition of Done (продукта целиком)
1. Все пять потоков выполнены по критериям готовности.
2. Полный контур: любая из ≥3 моделей, TP/EP по NVLink, tiering, спекуляция,
   оба API, дашборд, калибровка — всё работает и измерено.
3. Quality-gates не хуже референсов на всех поддержанных профилях.
4. Бенчмарки по контракту раздела 5 зафиксированы в `bench/results/` с ADR-записями.

---

## 5. Бенчмарк-контракт (фиксированный протокол)

- Метрики раздельно: TTFT, prefill tok/s, target-only decode tok/s, spec-decode tok/s, TPOT;
- контракт single-request: T=1, top-p=0.95, top-k=20, seed=0, до 256 выходных токенов;
- медиана 3 тёплых прогонов после 1 холодного, один успешный старт на версию;
- фиксируем: KV-dtype, batch, memory-utilization, версию CUDA/драйвера, часы GPU;
- каждое измерение кладётся в `bench/results/<date>-<slug>/` с логом `--report`;
- качество: GSM8K-32, HumanEval-32, PPL на фиксированном тексте — при любом
  изменении пути весов/KV/tier-политики.

Референсы для сравнения (нашего железа): 1Cat-vLLM v1.5.1 — GLM-5.3-Flash-NVFP4,
8×V100: 53.0 tok/s decode / 266 tok/s prefill; project-maya — 2×V100 PCIe:
54.5 tok/s, 4×V100 PCIe: 48.3 tok/s (prefill ~500 tok/s).

## 6. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| CUDA Graph несовместим с динамическим набором экспертов | высокая | слоты фиксированного размера + DMA; eager-фолббек внутри модуля |
| Prefetch-предсказание малоэффективно на редких экспертах | средняя | калибруемая политика; fallback LRU; hit-rate в дашборде |
| NVMe-тир медленнее RAM на конкретном NVMe | средняя | калибровка границ tier'ов; конфигурируемые пороги |
| SM70-ядра трудно отлаживать | средняя | операторные replay-фикстуры + golden-тесты |
| Параллельные потоки конфликтуют на стыках (engine↔tiers↔parallel) | высокая (командная работа) | контракты интерфейсов фиксируются ADR до старта потоков; интеграционные срезы каждые N недель |
| Объём «любая модель» разрастается | высокая | реестр растёт архитектурой за архитектурой; MoE — приоритет, dense — уже покрыт реестром |

---

## 7. Порядок работ (кратко)

1. Зафиксировать интерфейсные контракты модулей (ADR-08…ADR-12) — до старта потоков.
2. Запустить потоки A–E параллельно (A и B — критический путь).
3. Интеграционные срезы 1→4 по мере готовности модулей.
4. Финальный релиз — по Definition of Done раздела 4, с полным бенчмарк-отчётом.
