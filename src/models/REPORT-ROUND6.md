## [R1] `mlp.shared_expert_gate` → группа ffn.shared.gate_scalar

`src/models/src/hf_description.cpp` (ветвь Qwen2Moe-класса, shared-цикл
round 5):

- Тензор `model.layers.{layer}.mlp.shared_expert_gate.weight` (форма
  `[1, d_model]`, по факту шардов) → группа `l{layer}.ffn.shared.gate_scalar`
  (роль `attn` — как у групп `ffn.shared` round 5; dtype — исходный тензора:
  по прецеденту роутера — маленький служебный вес не квантуется, сигмоид/dot
  идут по F16/F32-пути).
- **Имя `gate_scalar`, не `gate`** — имя `ffn.shared.gate` занято матрицей
  `gate_proj` shared-FFN (ключ групп `ffn.shared.{gate,up,down}` в
  `ops_runner`, ADR-09 round 5). ADR-09 round 6 называет op `ffn.shared.gate`;
  имя группы в docs не зафиксировано — выбор зафиксирован здесь (D1) и
  размечен в коде.
- **Отсутствие тензора — группы нет** (обратная совместимость round 5):
  группы описаний без гейта побитово прежние (тест: подпоследовательность
  групп round-5 описания == round-6 описание без gate_scalar-групп, 48
  групп).
- **Частичный набор «gate есть, shared-FFN нет» → честный
  SchemaMismatch** (fail-fast; гейт без shared-FFN семантики не имеет).
  Обратная комбинация «trio есть, gate нет» остаётся валидной (round 5:
  фикстура OLMoE-класса, 48 групп) — «наоборот» из [Q5] (
  «план содержит gate-группу без ffn.shared») — это валидация ПЛАНА при
  загрузке, зона потока core (`ops_runner`), генератор такие планы не
  создаёт.
- Форма гейта обязана быть ровно `[1, d_model]` (`check_shape`) — по ADR-09
  round 6; отклонение формы реального чекпоинта — громкий отказ.

Семантика умножения (`sigmoid(dot(w_gate, hidden)) × shared_ffn_out`,
порядок суммирования `routed_sum → shared_contrib`) — `ops_runner`, поток
core ([R1] core-часть); описание и roundtrip проверены здесь побитово.

## [R2] dtype_orig в описании

- Round 5 зафиксировал dtype_orig в `Stats` конвертера
  (`groups_dtype_orig_bf16/f32`) и логе CLI — в description.json поля не
  было (R8-артефакт раунда 5: `dtype_orig=null`).
- Round 6: `hf_to_description` пишет **top-level поле `"dtype_orig"`**
  (сразу после `dtype_weights`) — его читает R8-обёртка serve/bench из
  description.json (`spec.desc.get("dtype_orig")`, ожидается строка
  `"bf16"`/`"f32"` — контракт serve-5, `tests/serve/test_r8_wrapper.py`).
- Значение — исходный dtype весов **до конверсии**, собирается по ВСЕМ
  расширенным группам (ровно множество конвертируемых тензоров):
  `F32→"f32"`, `F16+флаг bf16→"bf16"`, `F16→"f16"`.
- **Однородный источник → поле пишется; смешанный источник → поле НЕ
  пишется** (D2, честно: скаляр неоднозначен; полный состав — в Stats
  конвертера `groups_dtype_orig_bf16/f32` и логе CLI). Для реального
  tiny-qwen2moe (все тензора F32 — проверено read-only по шарду на сервере)
  поле будет `"f32"` — совпадает с ожиданием planner [Q6]
  («dtype_orig=f32/bf16»).
- Поле информационное: перегенерация не меняет слоты/логиты — тест
  сравнивает конвертацию описания С полем и БЕЗ поля (формат round-5):
  layout'ы побитово (group_id/data_offset/slot_bytes/crc32 по каждой
  группе) + логиты интерпретатора побитово. Парсер схемы 1.0 толерантен
  (неизвестные top-level ключи игнорируются) — прежние описания читаются,
  schema не менялась.
- CLI (`stell_hf_description`) изменений не требует — поле течёт через JSON;
  конвертер (`Stats`/лог) — без изменений (round 5). GGUF-путь
  (`gguf_to_description`) поле не пишет (D3: clamp-сатурация ADR-03 —
  HF F16/F32/BF16→F16 контур; GGUF-исходные dtype — отдельный учёт, см.
  «НЕ сделано»).

## Ключевые решения

- **D0.** База ветки — локальный `master` `41327b5` (== `server/master`);
  `origin` (GitHub) недоступен из среды (fetch падает), docs-коммиты
  раунда 6 в нём проверены на локальном `master` (e3b896b…41327b5).
- **D1.** Имя группы гейта — `l{layer}.ffn.shared.gate_scalar`:
  `ffn.shared.gate` занято матрицей gate_proj shared-FFN (round 5,
  `ops_runner` резолвит по этому имени). Требуется согласование с core-7
  (они резолвят гейт по имени группы в `ops_runner`).
- **D2.** `dtype_orig` — скаляр top-level (контракт serve-5); при
  однородном источнике пишется, при смешанном — честно отсутствует
  (состав — в Stats/лог конвертера). Не заводился per-group массив:
  схема 1.0 не менялась, парсер толерантен, скаляр покрывает контракт
  R8-обёртки.
- **D3.** dtype гейт-группы — исходный тензора (F16/F32; BF16→F16), не
  `dtype_weights`: по прецеденту роутера (маленький служебный вес,
  `source_group_dtype`); квантовать вектор 1×d_model смысла нет, а
  NVFP4-гейт потребовал бы нового декванта в ядре гейта.
