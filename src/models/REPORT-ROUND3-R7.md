## Потоковый дизайн

- **Память O(1) по payload'у модели:** источник читается последовательно по
  группам плана (шард за шардом для HF-чекпоинтов; для стековных тензоров
  GGUF-mixtral срезы соседних экспертов смежны — чтение последовательное и там).
  В RAM живёт ровно одна группа: слот (`slot_bytes`) + source-буфер
  (`make_slot`, при квантованном профиле — F32-буфер тензора) —
  O(максимальной группы), НЕ O(размера модели). В RAM держатся только
  метаданные — записи индекса (64 Б/группу, ADR-12 §2.2).
- **Раскладка = convert() побитово** (ADR-12 §2/§2.2/§2.4): заголовок 512,
  индекс на 0x200, данные монотонно с выравниванием 4096, без дыр. Тонкость
  формата: CRC32 группы известен только после записи её слота, а индекс
  обязан лежать ПЕРЕД данными → запись индекса с CRC-placeholder'ом, после
  каждого слота — перезапись своей 64-байтовой записи (fixup). Заголовок
  собирается сразу целиком (n_groups/смещения вычисляются из плана до записи).
- **Flush по группам:** `fflush` при накоплении ≥ `flush_group_bytes`
  (дефолт 8 МиБ) — данные уходят на NVMe по мере конвертации.
- **Атомарность:** файл пишется как `<name>.stelltier.tmp` и переименовывается
  по успехе + self-check собственным reader'ом (`stelltier_read_header_and_index`)
  перед rename — частичный файл не остаётся под финальным именем.
- **Старый `convert()` не тронут** — полная материализация осталась для
  сравнения/совместимости (тесты раунда 2 зелёные без изменений).

## Конфигурация тиров (согласование интерфейса с tiers)

`StellTierWriterConfig` (принимается извне; границы тиров задаёт tiers-конфиг —
`TierConfig`, `src/tiers/include/stell/tiers/tier_manager.hpp`):

- `vram_slot_size` — из tiers-конфига; writer валидирует план: каждая группа
  `slot_bytes ≤ vram_slot_size`, иначе профиль «свободно 2–11 ГБ на V100 при
  co-tenancy» неисполним → `SchemaMismatch` на этапе конвертации (fail-fast);
- `ram_capacity` — принимается извне для выравнивания интерфейса; **в layout
  семантики не имеет** (ADR-12: layout хранит ровно то, что нужно tiers,
  без семантики тиров) — проверено тестом (файл побитово не меняется);
- `slot_align`/`index_align` — фиксированы layout v1 (4096/512), кастомные
  значения отвергаются (новая версия формата — только через ADR, ADR-12);
- `flush_group_bytes` — порог flush'а по группам.

CLI: `stell_convert_streaming` принимает `--vram-slot-size/--ram-capacity/`
`--flush-mb` (конкретные числа профиля 2–11 ГБ — решение деплоя; writer только
валидирует план и не размещает тиры — размещение остаётся на стороне tiers).

## Метрика: пиковая память writer'а (замер теста, fork + wait4 ru_maxrss потомка)

Синтетическая MoE: **64 эксперта × 4 слоя**, d_model=256, d_ff=512, NVFP4,
vocab 1024 → 794 некешевых групп, **52.1 МиБ** слотов layout,
F16-источник **194.1 МиБ** (генерируется тестом в /tmp, не коммитится).

| Замер (потомок выполняет только конвертацию) | Значение |
|---|---|
| Пик **потокового** writer (`convert_streaming`) | **≈ 4.4–5.0 МиБ** |
| Пик **полного** writer (`convert`, все слоты в RAM) | ≈ 57.7–58.3 МиБ |
| Отношение потоковый/полный | **1 / 11.8–13.2** |
| Отношение потоковый/размер модели (52.1 МиБ) | **1 / 10.8–12.2** |

Вывод: память потокового writer'а — O(максимальной группы) (≈4.5 МиБ,
доминирует F32-буфер квантования тензора 512×256) — **не O(размера модели)**;
масштабируется на реальные профили (Mixtral-8x7B: ~26 ГиБ весов → пик
конвертации остаётся в единицах МиБ). Замер воспроизводим:
`ctest -R models_convert_streaming -V` (метрики печаются тестом).

## Тесты

- **До:** ctest **44/44** (бейзлайн master `dedb67e`) — все зелёные, не тронуты.
- **После:** ctest **45/45** (+ `models_convert_streaming`). Новые проверки:
  1. mini_moe (committed fixture): поток → layout → логиты интерпретатора
     engine (stell-tier путь) == committed golden-референсу того же плана
     (независимый Python-интерпретатор, max_rel=2.4e-07 ≤ tol=1e-03);
  2. большая синтетическая MoE (64×4): файл читается reader'ом models И
     reader'ом tiers (`TierLayoutReader`); слот через tiers-reader == слоту
     через models-reader; слоты loader'а StellTier == прямому
     NVFP4W4A16-лоадеру (**794 группы, побитно**);
  3. логиты интерпретатора по потоковому layout == референсу того же плана
     (прямой путь) — **побитно** (vocab 1024);
  4. пиковая память (изолированные потомки) — метрики выше;
  5. конфигурация: `vram_slot_size` меньше слота группы → `SchemaMismatch`;
     `slot_align != 4096` → `SchemaMismatch`; flush по группам (порог 1 Б)
     + `ram_capacity` извне — файл побитово == `convert()` (кроме created_ts);
  6. каталог HF-шардов (2 шарда): layout побитово == конвертации тех же
     тензоров одним файлом;
  7. реальные веса: честный PENDING (см. ниже).

## Честный pending

- **Прогон на реальных весах (Mixtral-8x7B) — PENDING, причина: «веса не
  предоставлены»** (по постановке planner'а [R7] — не блокер). Пайплайн и
  конфигурация закоммичены и покрыты синтетикой (срезы 1–6). Прогон включается
  без изменения кода: env `STELL_R7_REAL_WEIGHTS_DIR` (каталог safetensors-шардов
  HF) + `STELL_R7_REAL_DESC_JSON` (описание ADR-09 схемы 1.0) — тест печатает
  PENDING с этой причиной, пока env не заданы (не молчаливый успех).
- Замер p95-пауз слоёв / hit-rate prefetch на профиле co-tenancy — по [R7]
  это следующий пункт задачи (требует NVMe-тира и серверного окна); writer
  раунда готовит для него физический путь весов (layout срез 3).
- Память `convert_streaming` — O(максимальной группы), не строго O(1):
  при квантованном профиле материализуется F32-буфер тензора (4 Б/элемент
  максимальной группы) — конвенция `make_slot`, общая с `convert()`; для
  реальных весов это единицы МиБ (задокументировано в convert.hpp).
