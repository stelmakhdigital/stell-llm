## Карта GPU и разделение ролей

| Карта | Архитектура | Связь | Роль на сервере |
|---|---|---|---|
| GPU0–GPU3 | V100-SXM2-32GB (SM70) | NVLink | целевые карты: все замеры PLAN.md §5 (TTFT/tok/s/latency), scaling-бенч TP4, latency-бенч NCCL по NVLink |
| GPU4 | RTX 2060 (SM75) | PCIe | только контрактные/регрессионные CUDA-тесты и PTX-JIT смоук |

- **RTX 2060 (GPU4) пригодна для:** CUDA-контрактных/регрессионных тестов,
  PTX-JIT смоуков, корректности NCCL по fallback-транспорту (пара GPU0+GPU4,
  побитово == CPU-эталон).
- **RTX 2060 не пригодна для производительных замеров §5:** архитектурный
  класс и отсутствие NVLink делают её непригодной для scaling-целей
  (TP4 ≥3.2× определяется NVLink-парами V100). Все замеры на 2060 помечаются
  и **не сравниваются** с целями PLAN.md §5 и референсами.
- Latency-бенч NCCL — только пара V100-SXM2 по NVLink и только в более
  чистом окне, с пометкой co-tenancy.

## CUDA-сборка: PTX-JIT страховка

- **CUDA-сборка обязана включать PTX SM70 в gencode-списке** — автоматический
  PTX-JIT даёт работоспособность на новых архитектурах (подтверждено 7/7
  смоуков на RTX 2060).
- Отдельный PTX-only артефакт/конфигурация билда **не заводится** — PTX уже
  в fatbinary; дублирование функциональности и усложнение CMake без выигрыша.
- **Смоук dlopen+replay на нецелевой карте (RTX 2060) — штатный пункт
  серверного прогона.**

## Прогоны: только git-клон

- **Все прогоны — только через git-клон на сервере; scp-копирование
  артефактов запрещено.** Сборка, тесты и bench выполняются в клоне
  (например, `~/Code/stell-llm`), результаты коммитятся в `bench/results/`.

## Co-tenancy: правила окна

Сервер — co-tenancy со strata (держит 3 из 4 V100); правила окна:

- **Свободная VRAM.** Прогон планируется под фактический профиль
  «свободно ~2–11 ГБ на V100»; недоступные карты/объёмы — честный
  pending (`checks=0 failures=0`) с причиной, не молчание.
- **RTX 2060-квота.** GPU4 считается «второстепенной» картой: на неё
  выносятся только контрактные тесты/смоуки (см. таблицу выше), тяжёлые
  прогоны её не трогают.
- **`NCCL_P2P_DISABLE=1` при зависаниях P2P.** Зависание коллективов при
  `ncclCommInitRank COMPLETE` на парах 0↔3/2↔3 — типичный признак
  вмешательства co-tenancy в direct-pointer P2P; повтор с
  `NCCL_P2P_DISABLE=1` обязателен (корректность обязана подтверждаться
  и без P2P — ring через host).
- **Cold-замер без sudo.** `posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED)`
  по файлам тира (userspace, точечная eviction); sudo/DROP_CACHE запрещены
  spec. Fallback при недоступности fadvise — прогон помечается
  «тёплый (page cache)» в отчёте. Категоризация cold/warm и правила
  сравнения — round 5: см. ниже «Протокол I/O-замеров ([R2]/[Q8] round 5)».

## NCCL-транспорт: ограничение среды (заготовка, [R1] round 4)

Контекст: корректность GPU-контракта подтверждена single-card (world=1) и
CPU-контрактами; межкарточный транспорт между картами на сервере под
co-tenancy не поднимается — shm-attach failure. Диагностика round 3 показала:
наш код доходит до NCCL-вызова корректно, ломается именно межранковый
транспорт (не обвязка p2p/alltoall). /dev/shm исправен (32 ГБ, rw) —
подозреваемый: среда bootstrap при co-tenancy (зависания коллективов
наблюдались и в round 2 — консистентная гипотеза).

### Протокол экспериментов round 3 (пара GPU0+GPU4, PCIe)

1. **Попытка 1 — P2P (direct):** fail-fast, `ncclAllGather` → shm-attach
   failure. Честый pending (`checks=0 failures=0`), не выдан за pass.
2. **Попытка 2 — `NCCL_P2P_DISABLE=1`:** NCCL сам выбирает SHM-транспорт
   для intra-node P2P → снова shm-attach errno 115/11. Честый pending.
3. **Решающий эксперимент — single-card:** RTX 2060, world=1 →
   GPU-VALIDATION OK, `checks=1` (allreduce ≈ 0.8 µs). Логи —
   `bench/results/20261019-nccl-gpu-r3/`.

### Исход попытки 3 (round 4, worker-прогон 2026-10-19) — ограничение среды ФИКСИРУЕТСЯ

Попытка 3 (`NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1`, socket/NET) **не подняла
транспорт**. Протокол round 4 (пара GPU0+GPU4, `ncclGetLastError` теперь в
CommError):

1. Транспортная sanity (новая фаза 0, round 4b): попытка 1 — ncclAllReduce →
   `Error while attaching to shared memory segment /dev/shm/nccl-… (9.6 МиБ),
   errno 11/115`; попытка 2 (P2P_DISABLE) — WATCHDOG-тайм-аут 240 с (зависание
   коллектива); попытка 3 (SHM_DISABLE) — **`Failed to CUDA host alloc
   9641984 bytes`** на обоих ранках.
2. expert-фаза — те же три исхода; expert_alltoall не достигается (первый
   коллективный вызов падает раньше).
3. Вердикт по развилке `gpu_validation_verdict`: **Pending** (обе ветки сломаны
   средой) — не FailExpert (транспорт не подтверждён, атрибуция нашей обвязке
   невозможна).

Факторы среды, проверенные и отпавшие:
- `/dev/shm`: 32 ГБ, rw, пуст — исправен.
- `RLIMIT_MEMLOCK`: 8.2 ГБ — достаточно; **изолированный** `cudaHostAlloc`
  9.6 МиБ проходит (rc=0) — pinned-аллокат сам по себе работает.
- Single-card world=1 (RTX 2060): GPU-VALIDATION OK, checks=1 — NCCL и наш
  код корректны до межранкового bootstrap.

Итог: **ограничение среды фиксируется окончательно** — межкарточный
NCCL-bootstrap (shm-attach errno 11/115 + отказ CUDA host alloc внутри
многоранкового процесса при работающем одиночном) не поднимается под
co-tenancy strata. Гипотезы для чистого окна: вмешательство co-tenancy в
IPC/pinned-бюджет процесса, NCCL 2.26.2 + данное ядро/ОС. Межкарточная
корректность expert_alltoall/kv_stream — блокер среза 2 GPU-этапа, ждёт
чистого окна (пара V100+V100 без strata; `NCCL_DEBUG=INFO` + strace attach).
CPU-контракты + single-card подтверждение — постоянная база; фолбэка на
неподтверждённую корректность нет.

### Попытка 3 — socket-транспорт (план round 4, [R1])

- `NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1` — вынуждает NCCL на
  NET/sockets-транспорт между картами (штатная альтернатива SHM в NCCL
  2.26.2). `p2p_retry.hpp` расширяется с двух попыток до трёх;
  классификация pass/pending/fail и честный FAIL при
  confirmed-несовпадении сохраняются.
- **Если и попытка 3 не поднимет транспорт — ограничение среды
  фиксируется окончательно:** межкарточная корректность — блокер среза 2,
  ждёт чистого окна (пара V100+V100 без strata, приоритет при появлении;
  `NCCL_DEBUG=INFO` + strace attach — гипотеза «вмешательство co-tenancy
  в bootstrap» проверяется только там). Никакого «фолбэка» на
  неподтверждённую корректность. Этот пункт заполняется worker'ом по
  факту прогона.

> **Статус (round 4 → round 5):** попытка 3 исполнена (worker-прогон
> 2026-10-19) — транспорт не поднят (`Failed to CUDA host alloc 9641984 bytes`
> на обоих ранках); **ограничение среды фиксируется окончательно**
> (решение planner round 5 [Q2]). Дальнейшие попытки под co-tenancy
> **запрещены**; межкарточная корректность — блокер среза 2 GPU-этапа, ждёт
> чистого окна ([R7] round 5: пара V100+V100 без strata, исполнение
> протокола этого раздела — 3 попытки + транспортная sanity-фаза,
> `NCCL_DEBUG=INFO` + strace attach). Без окна — честный pending со
> статусом, вердикт не меняется; никаких обходов (не-NCCL транспорт,
> самописные P2P) и никакого «фолбэка» на неподтверждённую корректность.

## Протокол I/O-замеров ([R2]/[Q8] round 5)

Решение planner round 5 [Q8] (вердикт round 4: minor — pass; sudo не
вводится — spec запрещает sudo на любой машине):

- **cold = O_DIRECT — штатный честный cold-режим.** Бенч с `TierNvmeFile`
  O_DIRECT ([R2] round 4) снимает page cache-зависимость без root и без
  вмешательства в общесерверное состояние; активность подтверждается
  `odirect_active` в логе (round 4: true).
- **warm = buffered + fadvise (best-effort).** Fallback-режим с честной
  пометкой «тёплый»: fadvise под давлением page cache co-tenancy —
  best-effort по определению (подтверждено round 3); его «честная
  теплота» — честная пометка, а не фикция cold.
- **Обе категории I/O помечаются в артефакте** (`io_mode: odirect|buffered`);
  **сравнение ячеек допустимо только внутри одной категории I/O.**
  Cross-категорийное сравнение (O_DIRECT vs buffered) в вердикты не идёт —
  допустимо только как побитовая сверка корректности чтения (зафиксирована
  тестом round 4).
- **Per-group bench — дополнение ([R2]).** `bench_tiers_pause` принимает
  per-group layout: пауза слоя = сумма чтений групп слоя; hit-rate
  prefetch считается по группам (роли expert/attn/kv — из плана, ADR-09;
  layout v1 — «по 1 тензору на группу», слои в прод-профиле — множества
  групп, поэтому per-group суммирование — честная семантика цели §4,
  а не её ослабление). Uniform-слоты остаются синтетическим профилем.
  Прогон [R2] round 5: реальный layout tiny-qwen2moe (65 групп, 18.8 МиБ)
  с целевым профилем {4 МиБ-слоты + O_DIRECT + k=4} + сравнительная
  buffered-ячейка; co-tenancy-пометка, «НЕ вердикт §4»; артефакт в
  `bench/results/`. Дубль — в tiers.md.

## Формализованный критерий вердикта по цели §4 ([R3] round 6)

Решение planner round 5 [Q3] → [R3] (вердикт round 4: approve;
приоритет R1→R2→R4→R3). Сценарий §4 («MoE-модель больше VRAM (FP16-профиль)
декодируется с p95-паузой ≤ 5 мс и предиктором prefetch ≥ 60% попаданий»)
получает формальный критерий: измерение считается **вердиктом по цели §4**
только при выполнении ВСЕХ условий:

1. **(а) Модель больше VRAM-бюджета — тир реально работает.** Hit-rate < 1
   обязателен. Модель, целиком помещающаяся в VRAM (прецедент round 5:
   tiny-qwen2moe 18.8 МиБ при 31 VRAM-слотах, hit-rate 1.0000), не создаёт
   работы тира — её p95 измеряет DMA/планирование, а не тир; замер на такой
   модели вердиктом §4 **не является** (это точка регрессии warm-механизма).
2. **(б) Чистое окно ИЛИ честная co-tenancy-пометка с профилем остатка.**
   Замер обязан быть снят в чистом окне либо содержать в самом артефакте
   пометку co-tenancy с профилем остатка (какие карты/сколько ГБ свободны
   на момент замера). Co-tenancy-пометка только в commit-сообщении, без
   строк в артефакте (логи/README каталога) — условие не выполнено
   (прецедент round 5, judge I1).
3. **(в) Per-group семантика паузы.** Пауза слоя = сумма чтений групп слоя,
   hit-rate по группам (роли expert/attn/kv — из плана, ADR-09; round 5
   [R2]). Вердикт снимается только per-group bench; uniform-слоты —
   синтетический профиль и вердиктом §4 не являются.
4. **(г) Матрица {O_DIRECT, buffered} × {k=1, k=4}.** Вердикт выдаётся
   только для полной матрицы категорий I/O и глубины lookahead;
   сравнение ячеек — только внутри одной категории I/O (протокол round 5).

**Co-tenancy-замеры крошечных моделей НЕ валидны как вердикт §4** — даже
при соблюдении (в)/(г): цель §4 по определению — работа тира под
промахами, которой у модели в VRAM нет (прецедент round 5: p95
0.007–0.012 мс и hit-rate 1.0000 на tiny-модели честно помечены
«НЕ вердикт §4»). Если хотя бы одно условие нарушено — замер остаётся
точкой регрессии (с полным provenance, см. ниже) и не публикуется
как вердикт; честный pending лучше фиктивного вердикта.

## Точки регрессии обязаны иметь полный provenance ([R2] round 6)

Решение planner round 5 [Q6] → [R2] (вердикт round 4: approve).

- **Правило.** Каждая точка регрессии (bench-артефакт, golden-прогон,
  quality-gates report.json) обязана иметь **полный provenance**:
  host, дата/UTC, git-коммит, `co_tenancy`, warm/cold + `io_mode`,
  профиль (dtype/слоты/k), и — для артефактов с весами — **`dtype_orig`
  (исходный dtype каждой группы, ADR-03 «Уточнение round 5») и прочие
  поля provenance-схемы**. Артефакт с неполным полем provenance —
  неполная точка регрессии (прецедент: `dtype_orig=null` в report.json
  R8-точки round 4 — зафиксирована как неполнота, не задним числом
  подправлена).
- **Перегенерация.** Описания, используемые гейтами (минимум
  tiny-qwen2moe и далее), перегенерируются с полем `dtype_orig`;
  слоты/логиты до и после перегенерации обязаны совпадать побитово
  (конверсия не менялась — поле информационное). Для будущих конверсий
  поле обязательно по умолчанию.
- **Пометки — в самом артефакте.** Co-tenancy-пометки, «НЕ вердикт §4»,
  warm-механизм и прочие честные оговорки пишутся в файлы артефакта
  (логи/README каталога), не только в commit-сообщение (прецедент:
  judge I1 round 5).
- Обоснование: провенанс — часть правила честных замеров spec;
  точку регрессии с неполным provenance нельзя верифицировать при смене
  профилей. Стоимость перегенерации (~минута convert-цикла) несопоставима
  с ценой непроверяемой точки.

## Дополнение round 7 ([R1]/[R2], T-20261017200354, вердикт round 6: approve)

ADR-09 «Уточнение round 7» — qk-norm (`attn.q_norm`/`attn.k_norm`,
per-head RMSNorm `[d_head]`/`[d_kv]`, eps из config `rms_norm_eps`) и
опциональное поле
`router_renorm` (дефолт true; false — без перенормировки topk-весов,
config `norm_topk_prob=false`):

- **Перегенерация описаний.** Описания Qwen3Moe/tiny-qwen2moe-классов
  перегенерируются с q_norm/k_norm-группами (с eps) и полем
  `router_renorm`; точки на реальных весах (Qwen3-30B-A3B, 61 ГБ, вне git)
  после [R1]/[R2] обязаны иметь полный provenance по правилу round 6
  (`dtype_orig`, `co_tenancy`, `io_mode` и др.) — в самом артефакте,
  не только в commit-сообщении.
- **Сравнимость точек.** Точки до и после перегенерации описаний
  (появление qk-norm-групп и поля `router_renorm`, смена покрытия op) не
  сравниваются как идентичные без сопоставительной нотки в артефакте
  (прецедент judge I2 round 6: r5 vs r5-v2 — добавлено покрытие shared+gate,
  сменён профиль NVFP4→F16; изолирующий NVFP4-прогон возможен только
  после router_renorm — round 7).
- **NCCL-окно ([R6]).** Статус pending с условием не меняется; попытки под
  co-tenancy запрещены; при чистом окне — исполнение протокола этого
  раздела; потребность окна — пункт эскалации пользователю (не блокирует
  [R1]–[R4]).
