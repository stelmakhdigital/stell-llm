# ADR-12: Контракт tiers ↔ models — stell-tier layout на NVMe

- **Статус:** Принято (интерфейсный контракт, зафиксирован до старта потоков B и D;
  уточнено round 1, задача T-20261017200354 — см. «Уточнение» в конце: формат
  не меняется, устранены внутренние неконсистентности §2/§2.2/§2.3)
- **Стороны:** `tiers` (Tier Manager, NVMe-тир) ↔ `models` (лоадеры/конвертеры)
- **Правило изменения:** только через ADR и согласование с worker.
- **Связано:** ADR-03 (форматы), ADR-08 (тензорные группы), ADR-09 (разметка)

## Контекст

NVMe-тир tiers хранит веса в собственном формате **stell-tier** (ADR-03),
оптимизированном под io_uring-чтение: последовательные выровненные слоты,
индекс по тензорным группам. Кто владеет форматом: tiers читает/пишет файлы
layout, models (конвертеры) создаёт их из safetensors/GGUF/NVFP4-W4A16.
Контракт обязан быть зафиксирован до старта потоков B и D, чтобы конвертеры
и конвертируемость не блокировались друг о друга. Ключевое требование
PLAN.md §2.3: **tiers не знает про конкретные модели** — он оперирует
обезличенными тензорными группами с ролями (expert/attn/kv); layout хранит
ровно то, что нужно tiers, и ничего из семантики модели.

## Решение

### 1. Разбиение модели на группы (ответственность models)

Разбиение весов на тензорные группы — **исключительно на стороне models**
(ADR-09 §1, `tensor_groups`): по описанию модели веса распределяются в группы
с ролями `expert | attn | kv`, dtype целевого профиля (F16 / NVFP4 / W4A16)
и фиксированным `slot_bytes` (ADR-08). Конвертер в stell-tier:

```cpp
namespace stell::models {
// Конвертер «входной формат → stell-tier layout» (ADR-03).
// Точнее: принимает план групп (ADR-09) и пишет layout; tiers тут только читатель.
class IStellTierConverter {
public:
    virtual ~IStellTierConverter() = default;
    virtual void convert(const ModelDescription& desc,
                         const std::string& source_uri,   // safetensors/GGUF/NVFP4-W4A16
                         const std::string& out_dir) = 0; // пишет <uuid>.stelltier
};
} // namespace stell::models
```

Tiers принимает готовый layout и план групп (`ITierManager::set_plan`, ADR-08)
и не выводит ничего из содержимого сам.

### 2. Формат stell-tier (версия 1)

Один файл `<uuid>.stelltier` на модель/профиль. Все поля little-endian.
Магия, версия, выравнивание:

```
Заголовок (ровно 512 байт, выровнен на 4096):
  0x00  char[8]     magic      = "STLTIER\0"
  0x08  uint32      version    = 1
  0x0C  uint32      flags      = бит 0: checksum-таблица в конце (§2.3)
  0x10  uint64      created_ts (unix, метка конвертера)
  0x18  uint32      slot_align = 4096            // выравнивание данных групп
  0x1C  uint32      index_align= 512              // выравнивание записей индекса
  0x20  uint32      dtype_profile                // 1=F16, 2=NVFP4, 3=W4A16 (ADR-03)
  0x24  uint32      n_groups                     // число тензорных групп
  0x28  uint32      n_tensors                    // суммарно логических тензоров
  0x2C  uint32      header_crc32                 // CRC32 полей 0x00..0x28 — см. Уточнение
                                               // round 1: байты [0x00..0x2C), канон
  0x30  uint64      index_offset                 // смещение индекса (§2.2)
  0x38  uint64      data_offset                  // смещение первой группы данных
  0x40  char[96]    model_name (UTF-8, обрезано; только для удобства человека —
                                  tiers эту строку не читает)
  0xA0  …           reserved/padding (нулями до конца 512-байтового заголовка;
                                  см. Уточнение round 1 — «char[176]» здесь ошибочен)
```

### 2.2 Индекс тензорных групп (после заголовка, выровнен на 512)

Записей ровно `n_groups`, каждая — фиксированные 64 байта:

```
  0x00  uint32      group_id            // == ADR-08 GroupId (стабилен в файле)
  0x04  uint8       role                // 0=attn, 1=expert, 2=kv (ADR-08 Role)
  0x05  uint8       dtype               // 0=F16, 1=F32, 2=E4M3, 3=NVFP4, 4=W4A16
  0x06  uint8       tensor_count        // тензоров внутри группы
  0x07  uint8       reserved
  0x08  uint64      data_offset         // выровнен на slot_align, монотонно растёт
  0x10  uint64      slot_bytes          // размер слота группы (ADR-08, фиксирован)
  0x18  uint32      shape_rank
  0x1C  uint32      shape[4]            // до 4 измерений; больше — через tensor_count
  0x2C  uint32      crc32               // CRC32 слота группы целиком (payload+padding;
                                        // см. Уточнение round 1 о §2.3)
  0x30  char[16]    name (человекочитаемое имя, обрезано; tiers не читает;
                       см. Уточнение round 1 — «char[20]» здесь ошибочен)
```

Правила индекса:

- **Порядок записей = порядок групп в data-секции** (`data_offset` монотонно
  растёт, без дыр: io_uring читает длинными последовательными запросами —
  ключ к p95-паузам ≤ 5 мс, PLAN.md §4);
- `slot_bytes` в layout обязан совпадать с планом групп (ADR-08) — проверка
  при `set_plan`/открытии; mismatch = исключение `PlanMismatch`.
- Роль/dtype — из ADR-08; tiers не валидирует их относительно модели
  (он не знает модель), только переносит значения из плана в метрики/логи.

### 2.3 Контрольные суммы

- **header_crc32** — целостность заголовка (порча заголовка = файл невалиден).
- **crc32 каждой группы** — в записи индекса; tiers проверяет CRC при записи
  конвертером и при первом чтении группы в RAM-тир (не на каждом чтении —
  только один раз за жизнь файла в кеше tiers, чтобы не есть NVMe-пропускную
  способность).
- Повреждение CRC → `IoFailure` (уточнение round 1: `ChecksumMismatch`
  отсутствует в enum ADR-08 §3; см. Уточнение в конце),
  поведение (отключить группу/файл, деградация) — решение tiers, модель не задействована.

### 2.4 Выравнивание и размер

- Заголовок: 512 байт, выровнен на 4096 (начало файла).
- Каждая группа: выровнена на `slot_align = 4096` (NVMe-сектор × 8);
  `slot_bytes` кратен 4096.
- Минимальный размер чтения tiers — одна группа целиком (слот), без
  частичных чтений: layout не содержит кросс-групповых зависимостей.

### 3. Требование «tiers не знает про модели» — фиксация границ

- В код tiers запрещены: имена слоёв/экспертов/аттеншенов, знание о роутере,
  о профиле квантования как семантике (dtype — просто метка для выбора ядра
  dequant, ADR-09 §3), ветвления по `role` кроме метрики и логирования.
- Всё «модельное» живёт в models (разбиение, `source_pattern`, конвертеры)
  и в engine (план исполнения, `ops`).
- Тест на границу: CPU-тест tiers открывает layout, собранный из групп
  трёх разных архитектур реестра (1 dense + 2 MoE, PLAN.md §4) одним и тем же
  кодовым путём — поведение tiers не зависит от происхождения групп.

### 4. Обязанности сторон (сводка)

- **models:** JSON-описание (ADR-09) → план групп с ролями; конвертеры
  safetensors/GGUF/NVFP4-W4A16 → stell-tier; поддержка чтения stell-tier
  как входного формата лоадером `WeightsFormat::StellTier` (ADR-03, ADR-09 §3).
- **tiers:** владение layout на NVMe (io_uring, prefetch, CRC-проверки),
  сверка `slot_bytes`/dtype с планом (ADR-08), метрики тира.

## Альтернативы

- **Хранить stell-tier прямо в safetensors (просто переименовать файлы)** —
  safetensors не гарантирует выравнивание слотов под слоты ADR-08 и
  групповой порядок для io_uring; выбран отдельный формат.
- **SQLite/индексная БД вместо собственного индекса** — лишняя зависимость
  и случайный доступ вместо монотонного чтения; отклонено.
- **Tiers сам разрезает веса по ролям** — нарушает «tiers не знает про модель»;
  разбиение — всегда models (ADR-09 §1).

## Последствия

- Потоки B и D пишут независимо: B — реализует чтение/запись layout §2,
  D — конвертеры и лоадер stell-tier по той же спецификации.
- Один тестовый артефакт на стыке: fixture-файл `.stelltier` в `tests/fixtures/`
  генерируется конвертером D и потребляется CPU-тестами tiers (B) —
  это и есть интеграционная фиксация контракта без GPU.
- Изменение layout (например, новые dtype или 4+ измерений формы) —
  через новую версию `version` и ADR, с обратной совместимостью конвертеров.

## Уточнение (round 1, задача T-20261017200354)

Layout v1 не меняется (версия остаётся 1, бинарная совместимость не ломается);
ниже — устранение внутренних неконсистентностей §2/§2.2/§2.3, зафиксированных
по фактической реализации (`src/tiers/src/layout.cpp`,
`src/models/src/stelltier_format.cpp`). Маркеры «см. Уточнение round 1» в §2
указывают сюда.

- **Заголовок — ровно 512 байт (§2).** Поля 0x00..0x3F — как в §2;
  `model_name` — `char[96]` на 0x40..0x9F; **0xA0..0x1FF — нулевой
  padding/reserved (352 байта, всегда 0)**. Формулировка §2 «reserved
  char[176]» ошибочна (160+176=336 ≠ 512): реализация пишет нулевой паддинг
  до конца 512-байтового заголовка (`layout.cpp::finalize`: memset(hdr, 0,
  kTierHeaderSize)).
- **Имя группы — 16 байт (§2.2).** Поле `name` — `char[16]` на 0x30..0x40,
  заполняет запись ровно до 64; имя обрезается (`kTierGroupNameMax = 16`,
  `layout.hpp`). Формулировка §2.2 «char[20]» ошибочна (48+20=68 > 64);
  имя человекочитаемое, tiers его не читает.
- **CRC группы — по слоту целиком (§2.3).** CRC32 считается по слоту
  (payload + нулевой padding до `slot_bytes`), а не по «полезной нагрузке»:
  writer (`layout.cpp::add_group`) пишет слот нулевым паддингом и считает
  CRC по слоту; reader проверяет CRC при первом чтении группы (один раз за
  жизнь файла в кеше tiers).
- **Граница `header_crc32` (§2).** Канон — **CRC32 байтов [0x00..0x2C)**,
  т.е. поля 0x00..0x28 **включительно** (magic..n_tensors), до поля
  header_crc32. Так считает конвертер/лоадер stell-tier в models
  (`stelltier_format.cpp`, `crc32_ieee(h, 0x2C)` — writer и reader).
  **Отклонение, найденное в раунде кларификаций:** writer/reader в
  `src/tiers/src/layout.cpp` считают `crc32(hdr, 0x28)` (байты [0x00..0x28),
  без n_tensors) — файл, написанный `TierLayoutWriter`, читается
  `TierLayoutReader` (собственный roundtrip), но файл конвертера models
  `TierLayoutReader` НЕ примет (header CRC mismatch). Требуемое исправление
  (round 2, роль tiers): в `layout.cpp` заменить 0x28 → 0x2C в writer и
  reader; до исправления конвертированные файлы не скармливать NVMe-тиру
  (интеграционный срез 3). Канон выбран по производителю файлов (конвертер
  models — единственный прод-писатель layout, ADR-12 §4) и по инклюзивному
  прочтению исходной формулировки §2 «CRC32 полей 0x00..0x28».
- **`ChecksumMismatch` (§2.3).** На стыке tiers повреждение CRC →
  `TierError::IoFailure` (`ChecksumMismatch` отсутствует в `TierError::Code`,
  ADR-08 §3 — enum интерфейса не расширяется); `LoaderError::ChecksumMismatch`
  — код лоадера models (ADR-09 §3, реализован в `loader_stelltier.cpp`), на
  стык tiers↔models не выходит.
- **`n_tensors` (§2).** Семантика — суммарное число логических тензоров.
  Известное упрощение раунда 1: конвертер models пишет
  `n_tensors = n_groups` («1 тензор на группу», `stelltier_format.cpp`),
  writer tiers аккумулирует фактические `tensor_count`. Поле tiers не читает;
  расхождение — только в метаданных, к блокирующим исправлениям не относится,
  фиксируется честно.
