# ADR-09: Контракт engine ↔ models — декларативные описания, реестр, golden-тесты

- **Статус:** Принято (интерфейсный контракт, зафиксирован до старта потоков A и D)
- **Стороны:** `core` (engine) ↔ `models` (реестр архитектур, лоадеры весов)
- **Правило изменения:** только через ADR и согласование с worker.
- **Связано:** ADR-03 (форматы), ADR-08 (тензорные группы), ADR-10 (шардирование), ADR-12 (stell-tier)

## Контекст

Принцип PLAN.md §2.2: «новая модель = файл описания (+ ядро, если новая операция)».
Engine-планировщик не должен знать конкретные архитектуры; он исполняет операции,
которые ему выписывает описание модели, и передаёт tiers разметку тензорных групп.
Модули пишутся параллельно (потоки A и D), значит формат описания и интерфейс
загрузчика весов должны быть зафиксированы до старта.

## Решение

### 1. Формат описания модели — JSON (выбор и обоснование)

Выбран **JSON**, не YAML:

- конфиги архитектур (HF-референсы, `config.json`) уже JSON — golden-сравнение
  и миграция с референсов проще;
- в ядре C++20 JSON-парсер (nlohmann/json — header-only) проще и детерминированнее,
  чем YAML: меньше зависимостей, нет YAML-подвохов (типы `yes/no`, неоднозначные
  числа), CI на CPU-пути не тянет libyaml;
- описания моделей машинно-генерируются конвертерами (из `config.json`/GGUF-метаданных),
  человеку их редактировать редко.

Схема (версионная, поле `schema` — мажор.минор; неизвестные поля — ошибка парсинга):

```json
{
  "schema": "1.0",
  "name": "glm-5.3-flash",
  "class": "moe",                      // "dense" | "moe"
  "dtype_weights": "NVFP4",            // целевой профиль: F16 | NVFP4 | W4A16 (ADR-03)
  "vocab_size": 131072,               // числа — обычные int
  "d_model": 4096,
  "n_layers": 32,
  "n_heads": 64,
  "d_head": 128,
  "kv": {"dtype": "F16", "n_kv_heads": 8, "d_kv": 128, "quant": null}, // quant: "E4M3" (ADR-04)
  "moe": {                             // только для class=moe
    "n_experts": 128,
    "n_experts_active": 8,
    "expert_d_ff": 1024,
    "router": "softmax-topk"
  },
  "ops": [                             // операции engine, порядок = граф исполнения слоя
    {"op": "rmsnorm",   "io": ["hidden"],  "params": {"eps": 1e-5}},
    {"op": "attention", "io": ["hidden", "kv"], "params": {"kernel": "sm70_fp32_qk_pv"}},
    {"op": "moe_gather_scatter", "io": ["hidden", "experts"], "params": {"kernel": "sm70_moe_gs"}}
  ],
  "tensor_groups": [                   // разметка → tiers (ADR-08) и stell-tier (ADR-12)
    {"name": "l{layer}.attn.wq",  "role": "attn",   "shape": [4096, 4096],
     "dtype": "NVFP4", "source_pattern": "layers.{layer}.self_attn.q_proj.weight"},
    {"name": "l{layer}.kv",       "role": "kv",     "shape": [2048, 4096],
     "dtype": "F16",   "source_pattern": "layers.{layer}.kv_cache", "kv_block": true},
    {"name": "l{layer}.e{expert}.ffn", "role": "expert", "shape": [1024, 4096],
     "dtype": "NVFP4", "source_pattern": "layers.{layer}.mlp.experts.{expert}.weight",
     "cardinality": {"layer": 32, "expert": 128}}
  ]
}
```

Правила разметки:

- `tensor_groups` — единственный источник ролей `expert/attn/kv` (ADR-08);
  engine не выводит роли сам.
- `cardinality` — шаблон размножается по слоям/экспертам; `slot_bytes` каждой
  группы фиксируется при загрузке описания (до CUDA Graph, ADR-05/ADR-08).
- `source_pattern` — имя тензора во входном формате (safetensors/GGUF),
  привязка к лоадеру (§3).
- `ops` — операции engine; если операция не найдена в реестре ядра engine —
  ошибка загрузки модели («новая операция = новое ядро», PLAN.md §2.2).

### 2. Реестр архитектур (заголовок `stell/models/registry.hpp`)

```cpp
namespace stell::models {

struct ModelDescription {   // результат парсинга JSON (строго типизирован)
    std::string name;
    bool is_moe;
    // ... поля 1:1 из схемы §1; tensor_groups уже размножены по cardinality
    std::vector<stell::tiers::TensorGroup> groups;  // ADR-08 — готово к set_plan()
};

class IRegistry {
public:
    virtual ~IRegistry() = default;
    // Загрузка/валидация описания: schema-версия, операции, роли, cardinality.
    virtual ModelDescription load(const std::string& json_path) = 0;
    // Список встроенных архитектур реестра (цель PLAN.md: 1 dense + 2 MoE).
    virtual std::vector<std::string> available() const = 0;
};

} // namespace stell::models
```

Реестр растит архитектуру за архитектурой (PLAN.md §6); engine не имеет
if'ов по архитектурам — только `ops` и `groups`.

### 3. Интерфейс загрузчика весов (заголовок `stell/models/weights.hpp`)

```cpp
namespace stell::models {

// Лоадер переводит «входной формат» → заполненные тензорные группы (ADR-08).
// Форматы: Safetensors | GGUF | NVFP4W4A16 | StellTier (ADR-03).
enum class WeightsFormat { Safetensors, GGUF, NVFP4W4A16, StellTier };

class IWeightsLoader {
public:
    virtual ~IWeightsLoader() = default;
    virtual WeightsFormat format() const = 0;

    // Открывает источник весов и возвращает план групп, согласованный с описанием.
    // Ошибки — исключениями (единая политика с tiers, ADR-08 §3):
    //   LoaderError::Code { SchemaMismatch, TensorNotFound, ChecksumMismatch,
    //                       UnsupportedQuant, IoFailure }
    virtual std::unique_ptr<IWeightsSource> open(
        const std::string& uri, const ModelDescription& desc) = 0;
};

// Источник весов: групповое чтение для tiers (может быть файлом, pinned-памятью
// или уже размещёнными в VRAM буферами — CPU-путь без GPU обязан работать).
class IWeightsSource {
public:
    virtual ~IWeightsSource() = default;
    // Чтение группы по её GroupId (роль/dtype/shape берутся из плана, не из файла).
    virtual void read(const stell::tiers::GroupKey& key, void* dst, std::size_t dst_bytes) = 0;
    virtual void close() = 0;
};

} // namespace stell::models
```

Контракт отображения «формат → группы»: лоадер обязан по `source_pattern`
найти тензор, проверить dtype/shape против плана и заполнить буфер группы
(в целевом dtype профиля, dequant — ядрами engine/kernels, не лоадером).
Mismatch = исключение `SchemaMismatch`/`UnsupportedQuant` (тишина запрещена).

### 4. Golden-тесты логитов — часть контракта

Для каждой архитектуры реестра обязателен golden-тест (`tests/golden/`):

- фиксированный вход: промпт-токены, seed=0, greedy (T=1) — как в bench-контракте
  PLAN.md §5;
- эталон: логиты последнего слоя против HF-референса этой модели
  (фикстура `logits_ref.json`, допуски: rel ≤ 1e-3 для FP16-профиля,
  отдельные пороги для NVFP4/W4A16 — фиксируются в заголовке фикстуры);
- CPU-путь — обязателен и проходит локально без GPU; CUDA-вариант — на сервере.
- Тест прогоняется на трёх путях: обычный лоадер, stell-tier layout (ADR-12),
  tiering с принудительными промахами в NVMe-тир — логиты совпадают со входом
  того же профиля. Это фиксирует, что tiering не меняет вычисление.

Изменение формата описания или лоадера, ломающее golden-тест, запрещено.

## Альтернативы

- **YAML** — человечески приятнее, но: лишняя зависимость в C++-ядре, недетерминизм
  типов, нет выигрыша: описания генерируются конвертерами, а не пишутся руками.
- **Императивный код-описание модели (C++-класс на архитектуру)** — так сделано
  в тяжёлых стеках (vLLM-реестр): быстрое, но новая модель = компиляция, что
  противоречит принципу «файл описания» (PLAN.md §2.2).
- **Engine сам парсит конфиги моделей** — размазывает знание об архитектурах
  по engine; выбран отдельный модуль `models` с реестром.

## Последствия

- Потоки A и D пишут независимо: A — против `ModelDescription`/`ops`/`groups`,
  D — реализует реестр/лоадеры по фиксированной JSON-схеме.
- Разметка `tensor_groups` — единственный вход `ITierManager::set_plan` (ADR-08),
  и она же конвертируется в stell-tier layout (ADR-12) — один источник истины.
- Новая модель: JSON-описание + (если нужна новая операция) ядро; engine/kernels
  не трогаются для архитектур из существующих операций.

## Уточнение (round 1, задача T-20261017200354)

Контракт не меняется; ниже — фиксация конвенций, принятых при реализации
(`src/models`), по открытым вопросам раунда 1.

- **Имена тензоров GGUF (§3).** `source_pattern` всегда записывается в конвенции
  имён **входного формата**; лоадер сравнивает имя тензора с `source_pattern`
  буквально — никакого неявного маппинга HF-style ↔ GGUF (`blk.*`) нет
  (`loader_gguf.cpp`). Конвенция для генерации GGUF-описаний: паттерны —
  нативные имена llama.cpp-GGUF (`token_embd.weight`, `output.weight`,
  `output_norm.weight`, `blk.{layer}.attn_q.weight`, `blk.{layer}.ffn_up.weight`,
  `blk.{layer}.ffn_norm.weight`, …); описание для GGUF-источника генерируется
  конвертером как отдельный файл описания (реестр может держать несколько
  описаний одной архитектуры под разные семейства имён; `llama-class.json` —
  HF-стиль для safetensors). Обоснование: конвенции имён GGUF и HF несводимы
  простой заменой префикса (разная структура имён attn/ffn), маппинг в лоадере —
  скрытое знание о форматах; честнее генерировать описание под источник.
- **Greedy vs «T=1» (§4).** Поле `greedy: true` фикстуры golden — отдельный явный
  режим argmax: temperature не применяется, сэмплинг детерминирован.
  «T=1» bench-контракта PLAN.md §5 — другой режим: `temperature = 1.0`,
  `top_p = 0.95`, `top_k = 20`, `seed = 0` (дефолты `Scheduler::Sampling`,
  `scheduler.hpp`). Комментарий «T=1» в README golden-фикстуры — ссылка на
  bench-профиль, **не** синоним greedy; смешение режимов устранено:
  golden — greedy, bench — T=1.

## Уточнение (round 2, задача T-20261017200354) — единая раскладка NVFP4/W4A16

Контракт §3 (лоадер/группы) не меняется структурно; фиксируются конвенции
по расхождению «kernels vs models» в размере квант-блока (вопрос Q3 раунда 2).

- **Канон NVFP4/W4A16 — block32** (размер блока 32), как у models и ADR-03/ADR-09.
  Два разных размера блока в kernels и models — рассинхрон контракта dequant,
  который golden-тест обязан ловить; CUDA-версии dequant проверяются против
  CPU-референса на block32.
- **Смешанный план — явно:** квантованные группы (NVFP4/W4A16, block32) — только
  для **линейных весов**; неквантованные группы **F32/F16** — для норм/router/
  layernorm (и прочих нелинейных/малых тензоров). Это не исключение, а штатная
  форма плана: dtype — атрибут каждой `tensor_group` (см. схему §1), а не
  свойство профиля целиком.
- **dtype читается из группы, без fallback-догадок.** Лоадер (`IWeightsSource::read`)
  берёт dtype группы из плана (`GroupKey`/описание), не из эвристик по имени или
  формату файла; mismatch dtype/shape против плана — исключение
  `SchemaMismatch`/`UnsupportedQuant` (тишина запрещена — см. §3). Роль
  `tensor_groups` как единственного источника ролей и dtype (§1) подтверждается.
- **Group-16-фикстуры kernels — legacy (не-контракт).** Фикстуры с блоком 16
  в `src/kernels`/`tests` помечаются legacy: block32-варианты — единственные
  канонические; group-16 тесты не являются контрактными и не расширяются.
  Новые квант-блоки (Q5/Q6/Q2_K и прочие) — только с отдельным hex-эталоном
  по прецеденту models-2.

## Уточнение (round 5, задача T-20261017200354) — per-layer план и shared-expert

Контракт §1–§4 (схема, реестр, лоадеры, golden) не меняется; ниже — два
расширения интерпретации плана по решениям planner round 5
([Q4]→[R3], [Q5]→[R4], вердикт round 4: approve).

### Per-layer план ([R3])

- **Слои одного описания могут иметь разные op-профили.** Op-граф слоя
  определяется по наличию MoE-групп в слое: слой с группой `mlp.router`
  (и expert-группами) → MoE-контур; слой без неё → dense ffn путь.
  Формат плана уже per-layer (`tensor_groups` размечаются по `source_pattern`
  с `cardinality`, §1) — однородность профилей была реализационным
  ограничением интерпретатора плана (ops_runner), не формата описания.
- **Однородный план — частный случай, дефолт не меняется:** если все слои
  одного профиля, план интерпретируется как раньше; per-layer маршрутизация
  в ops_runner — обобщение, а не новая схема или новая версия `schema`.
- **Непокрытые конфигурации — честный SchemaMismatch.** Конфигурации, не
  покрываемые ни однородным, ни per-layer маршрутизатором (например, слой
  с частичным набором MoE-групп: router без expert'ов или наоборот) —
  честный отказ `SchemaMismatch` при загрузке описания/плана, не тихий
  неверный план (fail-fast §3 не ослабляется). Опциональный фильтр
  однородности в приёмке конвейера остаётся для моделей, не поддержанных
  per-layer.
- Обоснование: реальные MoE-классы (Qwen3-MoE, GLM-класс; SmolLM2-360M-MoE —
  3 плотных слоя из 31) массово содержат плотные первые слои; фильтр
  чекпоинтов по однородности отбрасывает большинство реальных чекпоинтов
  и делает критерий «3 архитектуры в полном контуре» (PLAN.md §4) фиктивным.
  Требования раунда: описание генерируется конвертером (`hf_to_description`),
  layout побитово == прямому лоадеру, логиты == референсу per-layer плана
  (тест на реальных весах вне репозитория).

### Оп-дополнение `ffn.shared` ([R4])

- **Shared-expert — dense-FFN группа `ffn.shared`** (gate/up/down, семантика
  обычного dense ffn): выход суммируется с суммой выходов routed-экспертов
  того же слоя. Новая операция ядра не вводится — переиспользуется
  существующий ffn-путь; аддитивное суммирование выполняет интерпретатор
  плана в ops_runner.
- **Обратная совместимость планов:** отсутствие группы `ffn.shared` в
  описании — поведение без изменений (аддитивного вклада нет); существующие
  однородные и per-layer планы валидны без перегенерации.
- Обоснование: Qwen2Moe/OLMoE содержат shared-expert с постоянным аддитивным
  вкладом в выход FFN — без него логиты структурно неверны (не аппроксимируются
  routed-экспертами), «честная пометка не поддержано» сделала бы срез 3
  некорректным по качеству. Движковый MoE-контур shared-expert не содержал;
  семантика «dense FFN + сумма» покрывается существующими ops. Требование:
  тест на фикстуре Qwen2Moe/OLMoE-класса со shared-экспертом — логиты ==
  референсу плана (побитово на CPU).

## Уточнение (round 6, задача T-20261017200354) — оп-дополнение `ffn.shared.gate_scalar`

Решение planner round 5 [Q5] → [R1] (вердикт round 4: approve). Схема §1,
контракты §2–§4 и уточнения round 1/2/5 не меняются; ниже — op-дополнение
к семантике shared-expert («Оп-дополнение `ffn.shared`» round 5).

- **Скалярный сигмоид-гейт — op `ffn.shared.gate_scalar`.** (Имя: контрактом раунда 5 имя `ffn.shared.gate` занято матрицей gate_proj shared-FFN — группы сосуществуют с разными именами; оба потока round 6 — core и models — пришли к `gate_scalar` независимо.) Реальные модели класса
  Qwen2Moe содержат тензор `mlp.shared_expert_gate` (форма d_model→1): выход
  shared-FFN умножается на скаляр
  `gate_scalar = sigmoid(dot(w_gate, hidden))`, где `w_gate` — тензор
  `d_model→1`, а `hidden` — вход FFN-контура слоя (тот же тензор, что питает
  router и shared-FFN). Итоговый вклад shared-эксперта:
  `shared_contrib = gate_scalar × shared_ffn_out`.
- **Порядок суммирования фиксируется явно (для побитового референса).**
  Итог MoE-контура слоя:
  1. `routed_sum` — сумма выходов routed-экспертов, накапливается в порядке
     следования expert-групп плана (без перегруппировки слагаемых);
  2. затем одной операцией добавляется
     `shared_contrib = gate_scalar × shared_ffn_out`;
  итог: `routed_sum + shared_contrib`. Без gate-группы —
  `shared_contrib = shared_ffn_out` (семантика round 5).
  Порядок сложения важен: плавающая сумма некоммутативна, побитовый
  референс требует фиксированного порядка — routed накапливается первым,
  shared-вклад (с гейтом или без) добавляется последним.
- **Группа плана.** Описание модели при наличии гейта содержит группу
  из тензора `mlp.shared_expert_gate` (форма `[1, d_model]`, роль — как
  у `ffn.shared`, обычно `expert`); `source_pattern` — имя тензора
  во входном формате (для Qwen2Moe-семейства — `mlp.shared_expert_gate`).
- **Отсутствие группы — прежнее поведение.** Нет `ffn.shared.gate_scalar` →
  аддитивный вклад без гейта (поведение round 5); существующие планы
  валидны без перегенерации (обратная совместимость, как round 5).
- **Частичный набор — честный SchemaMismatch.** Комбинация «gate есть,
  `ffn.shared` нет» (или наоборот после введения гейта в описание) —
  отказ `SchemaMismatch` при загрузке плана, не тихое игнорирование
  тензора (fail-fast §3; гейт без shared-FFN не имеет определённой
  семантики).
- **Реализация — ops_runner, новое ядро не вводится.** Умножение на
  скаляр — локальная операция интерпретатора плана; сигмоид и dot
  d_model→1 переиспывают существующие ops.
- **Требование (тест):** на реальном tiny-qwen2moe (чекпоинт вне
  репозитория) — описание покрывает gate, логиты интерпретатора ==
  референсу плана побитово; обнуление gate-веса даёт предсказуемое
  изменение логитов (не молчаливое игнорирование).

## Уточнение (round 7, задача T-20261017200354) — qk-norm и роутер без перенормировки

Решения planner round 6 [Q1]/[Q2] → [R1]/[R2] (вердикт round 6: approve;
[Q1]+[Q2] — одна amendment; judge I3 — побитовая референс-сверка на
реальном чекпоинте как пункт приёмки). Схема §1, контракты §2–§4 и
уточнения round 1/2/5/6 не меняются; ниже — два дополнения, завершающие
[R4] срез 3: конвейер реального чекпоинта Qwen3-30B-A3B (61 ГБ, вне git)
проходит по архитектурным причинам только после них.

### Группы `attn.q_norm` / `attn.k_norm` — per-head RMSNorm ([R1], [Q1])

- **Семантика.** RMSNorm, применяемая **независимо к каждой голове**:
  группы формы `[d_head]` (q_norm) / `[d_kv]` (k_norm; в поддержанных
  arch `d_kv == d_head == head_dim`; вес k_norm `[head_dim]` транслируется
  по ВСЕМ KV-головам GQA — реальный Qwen3-30B-A3B: n_kv_heads=4,
  тензор `[128]`; форма группы — per-head `[d_kv]`, НЕ `[n_kv_heads*d_head]`:
  регрессия поймана на реальном чекпоинте — фикстуры с n_kv_heads=1
  формы не различали, тест GQA n_kv_heads=2 добавлен) — вектор веса на
  голову — применяются
  к проекциям q/k **после** линейных проекций и **до** QK/PV-пути;
  нормализация каждой головы не смешивает элементы между головами —
  каждый `[d_head]`/`[d_kv]`-кусок скрытого состояния нормализуется
  собственной RMSNorm-строкой того же вектора веса. Внимание (реальный
  чекпоинт): dqq = n_heads*d_head может не совпадать с d_model
  (Qwen3-30B-A3B: 4096 != 2048) — o_proj `{d_model, n_heads*d_head}`, join
  голов без тождественной квадратной проекции. Роль групп — `attn`;
  dtype — dtype тензора источника по канону норм (F32/F16,
  BF16 → F16 clamp-сатурация, [R5] round 5).
- **eps — из config, не дефолт-догадка.** eps переносится из ключа
  `rms_norm_eps` файла `config.json` в описание (параметр op attention
  `qk_eps`); наличие q_norm/k_norm-группы при отсутствии `rms_norm_eps` →
  `SchemaMismatch` при загрузке описания (не молчаливое подставление
  значения по умолчанию). Валидация — **обе стороны**: op attention с
  qk-группами, но без параметра `qk_eps` → `SchemaMismatch`;
  `qk_eps` без групп attn.q_norm/attn.k_norm ни в одном слое →
  `SchemaMismatch` (мёртвый параметр).
- **Реализация — ops_runner, новое ядро не вводится.** Переиспользование
  rmsnorm-семантики по head-строкам — операция интерпретатора плана;
  decode-форма attention уже в контуре, CUDA-ядро не требуется (и не
  вводится — отдельного qk-norm CUDA-ядра в контуре нет).
- **Отсутствие ОБОИХ групп — прежнее поведение.** Нет ни `attn.q_norm`,
  ни `attn.k_norm` → план интерпретируется как раньше (Llama/Mixtral
  и побитовые golden не меняются).
- **Частичный набор — честный SchemaMismatch.** `attn.q_norm` без
  `attn.k_norm` (или наоборот) → отказ при генерации описания (конвертер)
  и при загрузке плана, не тихий
  неверный план (fail-fast §3: односторонне нормализованный attention
  не имеет покрытой семантики).
- **Обоснование.** Qwen3Moe-класс — целевой реестровый профиль (128
  экспертов, A3B); per-head RMSNorm — семантика attention-пути, а не
  «особенность чекпоинта». Зонд round 6: реальный чекпоинт Qwen3-30B-A3B
  содержит qk-norm `[head_dim]` в каждом слое. Фильтр в конвертере
  отвергается окончательно — эквивалентен «молча неверным логитам».
- **Требования (тесты):** (а) независимая побитовая референс-реализация
  forward per-head RMSNorm; (б) побитовые golden (dense/moe/mixtral) не
  меняются; (в) описание реального Qwen3-30B-A3B генерируется без
  SchemaMismatch; (г) логиты интерпретатора == независимому референсу
  плана (побитово на CPU; judge I3 — пункт приёмки среза 3).

### Опциональное поле описания `router_renorm` ([R2], [Q2])

- **Поле:** `router_renorm` — опциональное поле описания, `true|false`;
  **дефолт true** — текущая Mixtral-семантика канонизирована golden'ом
  round 1; `false` = topk-веса роутера используются **без
  перенормировки** (config-семантика `norm_topk_prob=false`, Qwen3Moe-класс).
- **Версионирование — опциональное поле с дефолтом, `schema` остаётся
  «1.0»** (правила ADR-09 для опциональных полей: бамп не потребовался).
  Поле в JSON-описание пишется **только при `false`** (config
  `norm_topk_prob=false`; при `true` или отсутствии ключа — поле не
  пишется). Дефолт гарантирует обратную совместимость: старые описания
  без поля = текущее поведение; побитовые golden (поле отсутствует →
  true) не меняются.
- **Реализация — ops_runner.** Флаг учитывается в MoE/router-контуре;
  перенормировка — переключатель внутри существующей op router, пара op'ов
  «router-renorm/router-norenorm» не заводится (дублирование пути).
- **Частичная настройка — честный отказ.** `router_renorm=false` при
  `class=dense` (роутера нет) → отказ при загрузке описания, не тихое
  игнорирование поля; в интерпретаторе плана — `SchemaMismatch`, если ни
  один слой не имеет `mlp.router`. В смешанном per-layer плане (round 5)
  на dense-слоях флаг не имеет эффекта и не мешает.
- **Перекрёстная сверка `moe_intermediate_size` (зонд round 6).** d_ff
  routed-экспертов берётся из фактической формы экспертного тензора
  первого MoE-слоя (`e{expert}.gate/up` — `[d_ff, d_model]`,
  `down` — `[d_model, d_ff]`; все эксперты всех MoE-слоёв сверяются
  между собой); config-ключ `moe_intermediate_size` при наличии сверяется
  против этой фактической формы тензоров; несогласованность
  config ↔ тензоры или экспертов между собой → `SchemaMismatch`
  (тест на Qwen3Moe-конфиге).
- **Обоснование.** tiny-qwen2moe config `norm_topk_prob=false` в round 6
  честно отвергался конвертером; после введения поля это легитимная
  конфигурация; изолирующий NVFP4-прогон (judge I2 round 6) возможен
  только после флага. Флаг с дефолтом true сохраняет побитовые контракты
  и честно отражает config-семантику модели.
- **Требование (тест):** побитовый референс router-пути без renorm;
  побитовые golden (поле отсутствует → true) не меняются.
